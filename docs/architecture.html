How Write_On is built

This is an unofficial replica of Write_On, the writing tool Jason Fried shows in his post on X, and not his own. The app is a small native Mac program wrapped around a web page. The Swift part owns the windows, the files, the key and the network. The page is the editor. This report walks through both, how they talk, where each behavior lives, and how the whole thing is tested.

The short version

The app is two programs in one bundle, joined by a narrow channel.

  • The shell is 13 Swift files built with SwiftPM. It makes the windows and the menu bar, reads and writes files, keeps the API key and talks to the AI service. It knows nothing about writing: a document passes through it as one string it never looks inside.
  • The page is the editor: 43 plain JavaScript modules, six stylesheets and one HTML file, with no framework, no bundler and no third-party code. It runs in a WKWebView, the system's WebKit view. It knows nothing about files, keys or the network.
  • The bridge between them carries 14 requests from the page, 6 events from the shell, and one question the shell asks the page.

Three ideas run through the code:

  • The document is data, and the screen is a rendering of it. Blocks and groups in memory are the truth. The paragraphs you see are drawn from them.
  • Whatever decides what the document is lives in pure functions. They need no browser, so 364 tests run against them in Node.
  • Nothing from outside is trusted. The page never holds the key. An answer from the model is checked against your own text before the app will act on it.

Two halves

The split was settled at the start: a WebKit editor inside a native shell. The original is a web app, so its text layout, selection and animation are a browser's. Rebuilding them with the same technology meant measuring the clips and setting the same CSS values. What a web page cannot be is a proper Mac citizen: a document window with a dot in its close button, save panels, Open Recent, Finder's Open With, the Keychain, recovery after a crash. That is the shell's job.

How the page is kept in its box

  • It loads from writeon://app/, a private URL scheme. AssetSchemeHandler serves it from the app bundle and fails any request that resolves outside the web root.
  • The web view refuses every navigation that is not writeon://app and never opens a second window.
  • browser.open accepts one address: https://x.com/intent/post. Anything else is refused.
  • The page is never given the key. It sends a request and receives text.

From double-click to a page you can type in

The bridge

All traffic between the halves goes through two small files: Sources/WriteOn/Bridge.swift (87 lines) and web/src/native.js (95 lines). There are three kinds of message.

  • The page asks. native.call(method, params) posts { method, params } to WebKit's message handler and returns a promise. The shell's handler for that method replies, and the promise resolves or rejects.
  • The shell tells. bridge.emit(event, payload) runs a line of JavaScript in the page that hands the payload to whoever called native.on(event, …).
  • The shell asks. bridge.ask(question) calls into the page and waits for the function registered with native.answer(question, …). It is used once.
// The page asks                              web/src/features/files.js
const outcome = await native.call('file.save', { text, as });

// The shell answers             Sources/WriteOn/DocumentWindowController.swift
bridge.on("file.save") { [weak self] params, reply in
    guard let self, let text = params["text"] as? String else { … }
    self.save(text, saveAs: params["as"] as? Bool ?? false) { saved in
        reply(.success(["saved": saved]))
    }
}

// The shell tells, and the page listens              web/src/main.js
bridge.emit("menu.command", ["name": name])
native.on('menu.command', ({ name }) => shortcuts.perform(name));

Inside the page

There is no framework and no build step. index.html loads src/main.js as an ES module, and that one file builds the whole app by hand. Each part is made by a function that receives exactly what it depends on:

// web/src/main.js, abridged
const editor       = createEditor(document.getElementById('editor'));
const decor        = createDecor({ svg, underlay, editor });
const sound        = createSound({ enabled: () => ui.get('sound') });
const alternatives = createAlternatives({ editor, ui, decor, sound, explosions });
const panel        = createPanel({ editor, ui, alternatives, commands });
const ai           = createAIClient(native);
const lab          = createLab({ editor, ui, ai, commands, cards });
const files        = createFiles({ editor, ui, commands, native, tooltips });

Reading main.js top to bottom tells you who depends on whom. The only global is window.writeOn, a handle on all of it for the console and for test scenarios.

Three things every part shares

  • ui in state.js holds seven interface flags: read, alternates, panel, overflow, lab, source, sound. Each is mirrored as a class on <body>, such as is-read, so the stylesheets do the showing and hiding.
  • commands in commands.js is a table of 16 named commands, from alternatives and ghost to save and undo. A shortcut, a right-click item, a toolbar icon and a menu-bar item all end in commands.run(name).
  • native in native.js is the bridge.

Layers

The shape of a feature

Features follow one pattern, which is what keeps 14 of them from tangling:

  • A function createX({ editor, ui, commands, … }) sets it up and returns a small interface.
  • It registers its commands, and listens to editor.on('change', …) and ui.on(…).
  • It changes the document only through editor.change(), never by editing the DOM.
  • Its reasoning lives in a pure module beside the model: features/ghost.js is 21 lines because doc/ghost.js works out what the command acts on. The same pairing holds for Overflow, the Lab (doc/proposal.js, doc/trim.js) and alternatives (doc/target.js, doc/model.js).

The document

In memory a document is three things: a list of blocks, a table of groups, and the Overflow text.

blocks   = [ { kind: 'h', level: 1, runs: […] },          // a heading
             { kind: 'blank', runs: [] },                // an empty line
             { kind: 'p', runs: [ { text: 'This one ' },
                                  { text: 'keeps', vid: 'k33ps01' },   // belongs to a group
                                  { text: ' the others too.' } ] } ]
groups   = { k33ps01: { scope: 'word', variants: ['keeps', 'remembers', 'holds on to'], active: 0 } }
overflow = 'Spare lines wait here.'

A block is a paragraph, a heading or a blank line. Its text is a list of runs, and a run may carry a group's id (vid) or be ghosted. A whole paragraph can be a group too. The text showing is always variants[active]. A position in the document is { block, offset }.

Rules that keep it sound

  • Groups do not nest. Variants are plain strings. Making a larger group over smaller ones turns the smaller ones back into text.
  • A group needs two variants. Left with one, it dissolves into plain text, which is why an underline disappears when you undo the last alternative.
  • Ghost text and groups never straddle. A ghost run that would cross a group's edge is split there.
  • Every edit ends with normalizeBlocks(). It turns a line starting # into a heading, removes duplicate ids left by splitting a paragraph, drops groups with no text left, and re-reads each group's showing variant from the text.

Blocks are never modified once made. Every function in doc/blocks.js returns new blocks, so a list of blocks is also a snapshot of the document. Undo relies on that.

The file

One Markdown file. The text comes first, as the piece currently reads. Overflow follows a marker line. The alternatives sit in one HTML comment at the end, which other tools ignore. This is the start and end of the welcome piece as the app saves it, 3,275 bytes in all:

# Write it more than one way

Most writing tools keep the last thing you typed. This one keeps the others too, …

<!-- overflow -->

Spare lines wait here.

<!-- write_on {"version":1,"html":"<p><br></p><p># <span data-vid=\"t1tle01\">Write it more than
one way</span></p>…","groups":{"t1tle01":{"scope":"sentence","variants":["Write it more than one way",
"Say it more than one way","Keep every version"],"active":0},…}} -->

doc/format.js (564 lines, the largest of the pure modules) converts between this text, the html record and blocks. Reading is forgiving and never throws:

  • If the Markdown still matches the recorded html, the record is used as it is.
  • If the Markdown was changed in another tool, the Markdown wins. Each group is kept where its showing text can still be found, looking first in the paragraph it was in. A note by the Open icon says how many were kept.
  • If the comment is damaged, the file opens as plain Markdown, with a note.
  • A piece with no alternatives and nothing ghosted is written as plain Markdown, with no comment at all.

How an edit happens

The editor is one contenteditable element whose children are paragraphs. editor/editor.js keeps the blocks and the DOM together with two kinds of edit, chosen in the beforeinput handler.

Details that matter

  • Rendering is a diff. Each block has a key that is equal for two blocks exactly when they render the same. render() compares keys from both ends and rewrites only the paragraphs in between.
  • The browser is checked. After its own edit, a paragraph that holds anything unexpected (an empty span, a style attribute, a stray line break) is rendered again from the block.
  • Undo is the document's own. doc/history.js keeps up to 500 snapshots of blocks, groups, Overflow and selection. Typing within 700 ms is one step, and each command is one step. WebKit's undo knows nothing about groups, so ⌘Z in the menu is routed to the page.
  • Paste and drop are plain text. Rich formatting commands are refused.
  • The marks are not in the text. editor/decor.js measures where each group's text sits and draws underlines, dots and margin bars in an SVG laid over the page. editor/wobble.js shapes each line from a seed, so an underline looks hand-drawn and looks the same every time.

One feature, traced: flipping a word

  1. A mousemove finds the group under the pointer. The arrow keys are that group's for as long as the pointer is what was last used: it has moved, clicked or scrolled since the last character was typed. Typing gives them back to the caret until the pointer moves again, so you can still edit an underlined word.
  2. A keydown on an arrow key calls cycle(vid, ±1). Right and down go forward, left and up go back, and they wrap.
  3. editor.change('alternative', …) sets the group's active and has showVariant() swap the text. For a word it also fixes a preceding a or an.
  4. The new text blurs in, and sound.tick() plays. ToneSession picks the pitch: low when you land back on the variant you started from, high otherwise.
  5. The change event fires. decor redraws the dots and files lights the Save icon.

The AI path

The page writes the question and judges the answer. The shell holds the key and does the asking. The model only ever sees a request the page built, and the page only ever sees text.

The Lab asks differently

A Lab pass sends the whole piece as numbered paragraphs, without the ghosted text, and requires the answer in a JSON shape. The model is never allowed to rewrite:

  • A trim is one question, whatever the level. The piece goes a sentence at a time, and for each the model sends back the sentence with what it could lose deleted and, from 1 to 5, how much the piece needs it. alignDeletion() in doc/trim.js accepts a shortened sentence only if it can be reached from your text by deleting words, and reports exactly which stretches went; one that was reworded loses nothing. chooseCuts() then counts out what the level takes: what sentences could lose first, then whole sentences, the least needed first, each level holding what the lighter ones took. The one answer serves all four levels.
  • A mark or a typo must quote a passage that occurs in your text, or it is discarded.
  • Nothing changes until you say so. A proposal is held beside the document (doc/proposal.js) and shown with temporary spans that the editor ignores when it reads the page back. Accepting it is one editor.change().

This model reasons before it answers, and that reasoning counts against its token limit. So a Lab request asks for room to think as well: 2,000 tokens plus 6 a word for a trim, 1,000 plus 4 a word for the other passes, up to 32,000. The counting is the app's because the model cannot do it quickly. Asked to cut a piece to a number of words, a request for each level, it counted its way there one word at a time: 24 seconds to over two minutes a level on the welcome piece, and on a 500-word draft "Cut in half" took three and a half minutes and came to 8%. Asked what each sentence could lose it mostly answers without thinking: 4 to 25 seconds for all four levels, each within a point or two of what it says.

Settings

The Settings window (⌘,) takes a key, another address, the format, another model and the sound switch. A key typed there goes into the Keychain; one found in the environment or the login shell is held in memory only. With another address the app asks that service in LunaRoute's place: anything that speaks OpenAI's chat completions or Anthropic's messages (Format says which, or leaves it to the address), a model served on the same Mac included, which is asked without a key if there is none. A key under LunaRoute's own name in the environment is sent to LunaRoute and to no other service. Test connection asks a one-word question and says which key it used. Nothing in the shell prints or logs a key, and a key the service quotes back in an error is taken out before the line is shown.

Files and windows

One window is one DocumentWindowController, one web view and one document. AppDelegate keeps the list. The two halves split what they know: the page can say whether the document has unsaved changes, and the shell knows which file it belongs to.

Closing, crashing, and more than one window

  • Closing with unsaved changes is the one time the shell asks the page a question. The shell shows Save, Cancel, Don't Save. On Save it calls bridge.ask("save"), the page runs the sequence above, and the window closes only if the answer is { saved: true }. Quitting does this for each unsaved window in turn.
  • Drafts. At most every three seconds the page hands unsaved work to the shell with draft.write. The shell keeps it as a JSON file in ~/Library/Application Support/Write_On/Drafts and deletes it when the document is saved or let go. At launch, every draft still there reopens as an unsaved document.
  • If only the page dies, the shell reloads it. The page asks doc.start again and gets its draft back, or its file.
  • Opening a file uses the window that already has it, else a window nobody has written in, else a new one.
  • Reading tries UTF-8, then an encoding the file declares, then Latin-1, so a file is never refused for its encoding.

Build and packaging

  • No Xcode project. Package.swift declares one executable target for macOS 13 and later, with no dependencies. The Command Line Tools are enough to build it.
  • scripts/build-app.sh runs swift build twice, then assembles build/Write_On.app by hand: the binary, Info.plist, a copy of web/ in Resources, and the icon. It signs the bundle ad hoc.
  • The app is universal. It is built once for Apple silicon and once for Intel, and lipo joins the two executables into one; SwiftPM builds for both at once only with Xcode. Each half has a build folder of its own under .build/universal, because SwiftPM keeps one plan to a folder, and in a shared one a build can be handed the plan made for the other half. The scenarios run on whichever half suits the Mac, or on the one WRITEON_ARCH names. The Intel half has run only under Rosetta: no Intel Mac has run it.
  • Nothing of the Mac that built it goes with it. What a debugger would use to find the source names every file by its full path, home folder and all. A release build has those entries taken out with strip -S.
  • scripts/package.sh makes the copy a release carries: the app built afresh and zipped. It opens the zip again to see that the signature holds, that both halves are there and that neither this Mac's name nor a home folder's path is in it, and it will not package a working copy with changes that are not committed.
  • The version is kept in one place. CFBundleShortVersionString in packaging/Info.plist: three numbers, read as Semantic Versioning reads them. The README says what each promises, and the first scenario checks that the built app reports it in that form. CFBundleVersion beside it is the build, a whole number that goes up with each release.
  • The page ships as source. The files in the bundle are the files in web/, unprocessed.
  • The icon is drawn by code. scripts/make-icon.swift draws the app's own mark, a W with the pen stroke and three dots, at every size macOS asks for.
  • Fonts are bundled: IBM Plex Mono and Caveat, both under the SIL Open Font License. scripts/fetch-fonts.sh records where they came from and checks them by hash.
  • It registers as an editor for Markdown at the rank Alternate, so it appears under Open With without taking over your .md files.
  • It is not notarized. It is signed ad hoc, by the Mac that builds it, so macOS refuses a copy downloaded from a release until it is told to open it. Because each build is signed anew, macOS may ask once after a rebuild for permission to read the saved key.

The order it was built in

The work followed the layers from the bottom up. First came the evidence: the three clips in the thread, measured frame by frame and by audio analysis. Then a written spec, in which every behavior is marked as observed, stated by the author, or inferred, and a plan of 23 tasks. Each task was built test first. A fresh reviewer then read the whole branch, and one pass fixed what it found.

The two harness commits in mid-afternoon are there because the first scripted runs took the keyboard and the pointer from the person at the Mac. They moved the runs into the background and then made them fully headless, and the harness has failed any run that comes to the front ever since.

A second pass followed on 12 October, after the app had been used for real, and is not on the chart. It changed who the arrow keys belong to (a click on an underlined word no longer takes them away), seated the dots on the display's own pixels so that they can be seen on a 1x display, put the caret in the text from the moment a window opens and kept it out of the page's faded edges, and made a keystroke in a long piece cost about a third of what it did. An independent pass through the clips then found a dozen behaviors that differed from the original: undo around alternatives, where the caret goes when a word is flipped, trim levels that are there at once, and several smaller ones. The measurements behind the speed work are in tests/perf and the README's section on speed.

Readying the repository to be published, on 12 and 13 October, is not on the chart either. Besides the license and the documents a stranger needs, it let the AI client ask services other than LunaRoute properly: names of the app's own for the key, the address and the model in the environment, a service asked without a key, and the two parts of a request that OpenAI's service refuses asked for again in its way. It taught it Anthropic's way of speaking beside OpenAI's, and to ask again with more room when a model's thinking uses its room up. It made three rules about where a key may go: one under LunaRoute's name goes to LunaRoute only, plain http goes no further than the Mac's own network, and a request is never sent on to where an answer points. And it shut scripted runs in. One scenario had been putting its last question, with a made-up key, to LunaRoute's real address; a scripted run is now given nothing of the tester's own settings, and its client asks nothing that is not on this Mac.

The first use of that build, on 13 October, changed two more things. Trims had been asked for a level at a time, the model told how many words to reach, and on a real draft that took minutes and missed by a wide margin; they are now asked for once, a sentence at a time, and counted by the app (The Lab asks differently, above). And the card behind the M↓ icon gained a tab ahead of the original's two: the piece as Markdown, to copy, without the record the file keeps for the app. The same day the version became three numbers, and the build became universal (Build and packaging, above).

Known gaps

Where it had to guess

The original is not released, so the clips and the author's replies are the whole specification. Section 9 of the spec lists 54 decisions the clips do not settle, each in one row so it can be challenged. The README summarizes them.

Differences from the original

  • Lines are 36 px apart, not 36.4, and Overflow's are 22, not 22.5.
  • WebKit draws a selection that runs past the end of a line a little differently.
  • Trims take much longer.
  • The proposal card's width for the two strongest trims is extrapolated; the clips show only the first two.

Left open after the review

  • Editing a group's text in the page until it matches another of its variants leaves two identical variants.
  • A paragraph that reads exactly <!-- overflow --> is taken for the marker when the file is opened again.
  • Text dragged from the page into Overflow takes two undos to put back.
  • Finding the key runs your login shell as a terminal would, so ~/.zshrc is executed once. The README says so.
  • In the panel, emptying the row of a group's only variant leaves the row blank until the next change.
  • The note about recovered work also shows when only the page's process restarted.
